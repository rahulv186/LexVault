# LexVault ZK Prototype

LexVault uses this first zero-knowledge proof to demonstrate a real Groth16 workflow without pretending to prove the entire forensic pipeline.

## Circuit

Circuit: `evidence_commitment`

The circuit proves knowledge of private field values that produce a public commitment:

```text
commitment = evidenceHash^2 + evidenceHash * blinding + blinding^2
```

## Private Inputs

- `evidenceHash`: a field element derived off-chain from the evidence record's stored SHA-256 fingerprint.
- `blinding`: a deterministic private field element derived during proof generation and never persisted.

## Public Inputs

- `commitment`: the circuit-friendly public commitment emitted by the circuit.

## What This Proves

The prover knows private witness values corresponding to the public commitment.

## What This Does Not Prove

This circuit does not prove SHA-256 over an arbitrary evidence file inside the circuit. LexVault still computes and stores SHA-256 off-chain for evidence integrity. This ZK circuit is a small, field-friendly proof demo associated with an evidence record.

It also does not prove AES-256-GCM encryption, IPFS storage, PostgreSQL state, or custody-chain hashing.

## Development Trusted Setup

The setup generated by these scripts is for local prototype and hackathon demonstration only. Groth16 requires a Powers of Tau file and a circuit-specific proving key. The local scripts create those artifacts reproducibly, but this is not a production trusted setup ceremony.

Generated files are written to `zk/build/` and are intentionally ignored by git.

## Commands

Install local dependencies:

```bash
npm --prefix zk install
```

Compile the circuit and generate development proving artifacts:

```bash
npm --prefix zk run setup
```

Generate a proof:

```bash
printf '{"evidence_id":"EV-2026-000001","sha256":"<64 hex chars>"}' | npm --prefix zk run prove
```

Verify a proof:

```bash
printf '{"proof":{...},"public_signals":["..."]}' | npm --prefix zk run verify
```

## Backend Flow

1. Authenticated user requests proof generation for an evidence ID.
2. Backend loads the evidence record and its stored SHA-256 fingerprint.
3. Backend calls the local ZK prover with the evidence ID and SHA-256.
4. The private witness is used only in the Node process and is not stored.
5. Backend stores proof metadata, proof JSON, and public signals.
6. Verification calls `snarkjs.groth16.verify` with the verification key, proof, and public signals.
